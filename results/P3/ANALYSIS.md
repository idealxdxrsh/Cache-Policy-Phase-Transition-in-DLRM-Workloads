## 2. Cache organisation in the simulator

- One cache per table. `trace_sim/run_trace_sim.py` `run_sweep` builds one job per (policy, capacity, table) and `run_one` creates a fresh cache for each, replaying only that table's trace. Results record `capacity_unit: "vectors, one cache per table"`.
- So "256 vectors" means 26 separate 256-entry caches (at most 6,656 entries in total; tables with fewer than 256 unique ids never fill theirs), not one 256-entry cache.
- The "all" rows in `hit_rates.csv` are sums of hits and misses over the 26 independent caches (`aggregate`), not a shared-cache simulation.

A single shared 256-entry cache would require:
- One interleaved trace in request order. The loader reads Criteo row by row, but splits ids into 26 per-table lists, and skips empty fields, so the dumped `table_XX.u32` files no longer line up by row; they cannot be re-interleaved. It needs a new trace (e.g. per row, C1..C26 in column order, with row index kept).
- Keys that include the table, e.g. (table, id): ids are per-column hashes and the same value can appear in two columns but refers to different embedding rows.
- One cache instance per (policy, capacity) over all tables. This removes the per-table array parallelism: one job replays all accesses (46,128,690 at 2M, 231,492,097 at 10M, `dump_log.txt`). Belady's `prepare` would need next-use positions over the whole interleaved trace.
- The interleaving order is a modelling choice (row order, batch order) and should be stated.

Current code: not supported. There is no shared-cache mode or table-qualified key, and the dump format drops row alignment.

## 3. Does LRU beat LFU at any capacity?

Checked every capacity 64..100,000 (11 values) by comparing hit counts exactly.

- 2,000,000 rows, combined (all 26 tables), LFU persist: LRU never beats it.
- 2,000,000 rows, combined (all 26 tables), LFU reset (LFURP): LRU never beats it.
- 2,000,000 rows, large, combined, LFU persist: LRU never beats it.
- 2,000,000 rows, large, combined, LFU reset (LFURP): LRU never beats it.
- 2,000,000 rows, individual large tables, LFU persist: LRU never wins.
- 2,000,000 rows, individual large tables, LFU reset (LFURP): LRU never wins.

- 10,000,000 rows, combined (all 26 tables), LFU persist: LRU never beats it.
- 10,000,000 rows, combined (all 26 tables), LFU reset (LFURP): LRU never beats it.
- 10,000,000 rows, large, combined, LFU persist: LRU never beats it.
- 10,000,000 rows, large, combined, LFU reset (LFURP): LRU never beats it.
- 10,000,000 rows, individual large tables, LFU persist: LRU never wins.
- 10,000,000 rows, individual large tables, LFU reset (LFURP): LRU never wins.

LRU does beat LFU on some individual small tables: at 256 vectors, 10M rows, persistent LFU loses on tables 1, 4, 10, 12, 14, 17 (see `SUMMARY.md`); none of these is in the large set.
